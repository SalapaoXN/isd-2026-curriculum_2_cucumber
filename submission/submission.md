# CUCUMBER — คำอธิบายชุด Submission

เอกสารนี้สรุปว่าไฟล์ในโฟลเดอร์ `submission/` คืออะไร และควรดูไฟล์ไหนเมื่อต้องการตรวจงาน

## 1. งานนี้ทำอะไร

CUCUMBER เป็นระบบถาม–ตอบข้อมูลหลักสูตร โดยนำข้อมูลหลักสูตรที่ผ่านการ OCR และจัดโครงสร้างแล้วมาเก็บเป็นข้อมูลที่ค้นหาได้ จากนั้นระบบสามารถตอบคำถามเกี่ยวกับรายวิชา เช่น

- ชื่อวิชาและหน่วยกิต
- วิชาเรียนอยู่ปี/ภาคการศึกษาใด
- วิชาบังคับก่อน
- เนื้อหาที่เรียนในรายวิชา
- รายวิชาในแต่ละปี/เทอม
- การเปรียบเทียบแผนการเรียนบางกรณี

คำตอบถูกออกแบบให้มีข้อมูลอ้างอิงกลับไปยังหน้าต้นทางของหลักสูตร (provenance) เพื่อให้ตรวจสอบได้ว่าคำตอบมาจากข้อมูลส่วนใด

ชุด submission นี้ใช้ข้อมูลหลักสูตร **IT** และครอบคลุม 2 แผน คือ

- `coop` — แผนสหกิจ
- `no_coop` — แผนไม่สหกิจ

---

## 2. ภาพรวมการทำงานแบบสั้น

```text
เอกสารหลักสูตร
    ↓
OCR / แยกข้อมูล
    ↓
จัดข้อมูลเป็นโครงสร้าง
    ↓
ตรวจและแก้ข้อมูล
    ↓
curriculum.json
    ↓
แปลงเป็น SQLite + ข้อมูลสำหรับค้นหา
    ↓
ระบบถาม–ตอบ
    ↓
คำตอบ + แหล่งอ้างอิง
```

ระบบ QA แบ่งการค้นหาภายในเป็น 3 ลักษณะ

- **Structured** — ใช้ข้อมูลที่เป็นช่องชัดเจน เช่น รหัสวิชา ปี เทอม หน่วยกิต หรือ prerequisite
- **Semantic** — ใช้ค้นหาจากความหมายของคำอธิบายรายวิชา เช่น “วิชานี้เรียนเกี่ยวกับ cloud อะไรบ้าง”
- **Hybrid** — ใช้ข้อมูลทั้งสองแบบร่วมกัน

ผู้ใช้ไม่ต้องเลือกวิธีค้นหาเอง ระบบเป็นผู้เลือกให้

## 3. ไฟล์ที่ส่ง

### `schema/curriculum.schema.json`

JSON Schema สำหรับกำหนดรูปแบบของ `curriculum.json`

ใช้ตรวจว่าโครงสร้างข้อมูลหลักสูตรอยู่ในรูปแบบที่ระบบกำหนด

### `schema/schema.sql`

โครงสร้างฐานข้อมูล SQLite ที่ใช้เก็บข้อมูลสำหรับระบบ QA เช่น รายวิชา แผนการเรียน ตำแหน่งของวิชา และ provenance

### `curriculum.json`

ข้อมูลหลักสูตร IT ที่จัดเป็นโครงสร้างแล้ว

ภายในมีข้อมูล เช่น

- รหัสวิชา
- ชื่อวิชาภาษาไทย/อังกฤษ
- หน่วยกิต
- หมวดและประเภทวิชา
- ปีและภาคการศึกษา
- prerequisite
- คำอธิบายรายวิชา
- ตำแหน่งหน้าต้นทางของข้อมูล

ข้อมูลแยกตามแผน `coop` และ `no_coop`

### `curriculum.conversion.json`

บันทึกกระบวนการแปลงและซ่อมข้อมูลก่อนเป็นข้อมูล submission

ใช้แสดงว่าข้อมูลผ่านขั้นตอนใดมาบ้าง เช่น extraction, การแก้ชื่อด้วย LLM และ deterministic repair

### `curriculum.db`

ฐานข้อมูล SQLite ที่สร้างจากข้อมูลหลักสูตร

เป็นรูปแบบที่เหมาะกับการ query และใช้ร่วมกับระบบ RAG/QA

### `verify.json`

ผลการตรวจคุณภาพข้อมูลหลักสูตรด้วยกฎ deterministic

ไฟล์นี้แยกผลตรวจเป็นหลาย check เพื่อให้เห็นว่าประเด็นใดตรวจอัตโนมัติได้ และประเด็นใดต้องอาศัยการตรวจจากต้นฉบับโดยมนุษย์

> หมายเหตุ: `schema_validation` ในไฟล์นี้เป็น `PASS`  
> แต่ summary ของ verifier เป็น `EXCEPTION` เนื่องจากบาง check ไม่มีข้อมูลเพียงพอให้สรุปอัตโนมัติ หรือเป็นกรณีที่ต้องเทียบกับต้นฉบับหลักสูตร ไม่ได้หมายความว่าโปรแกรมทำงานล้มเหลว

### `gold_questions.json`

ชุดคำถามมาตรฐานสำหรับทดสอบระบบจำนวน **30 ข้อ**

แบ่งเป็น

- Easy 15 ข้อ
- Medium 10 ข้อ
- Hard 5 ข้อ

คำถามครอบคลุม structured, semantic และ hybrid QA รวมถึงกรณีที่ข้อมูลไม่มีอยู่ในหลักสูตร

แต่ละข้อมี expected answer/evidence และ provenance สำหรับใช้ตรวจผลของระบบ

### `eval_result.json`

ผลการรันระบบกับ Gold Questions ทั้ง 30 ข้อ

ผลสรุปของการรันชุดนี้:

- รันสำเร็จ: **30/30 ข้อ (100%)**
- Answer correctness:
  - PASS: **24**
  - PARTIAL: **1**
  - FAIL: **2**
  - REVIEW: **3**
- Strict correct: **23/30 (76.67%)**
- Provenance correct: **29/30 (96.67%)**
- Evidence correct: **28/30 (93.33%)**
- กรณี not-found ที่กำหนดไว้: **2/2 ถูกต้อง (100%)**
- Semantic evidence coverage: **51/53 (96.23%)**
- Latency เฉลี่ยประมาณ **7.69 วินาที/คำถาม**
- ไม่มี execution error

ค่า `REVIEW` หมายถึงกรณีที่การตัดสินความถูกต้องของคำตอบเชิงความหมายไม่เหมาะกับการเทียบข้อความแบบตายตัว จึงแยกไว้ให้ตรวจด้วยมนุษย์แทน

## 4. Provenance คืออะไร

ทุกข้อมูลสำคัญพยายามเก็บตำแหน่งต้นทางไว้ เช่น

```text
program: IT
source_filename: it_page_328.png
source_page: 328
document_category: description
```

ดังนั้นเมื่อระบบตอบข้อมูลรายวิชา สามารถย้อนกลับไปตรวจหน้าของเอกสารต้นทางได้

จุดประสงค์คือไม่ให้ระบบตอบโดยไม่มีหลักฐานจากหลักสูตร

---

## 5. กรณีที่ไม่มีข้อมูล

ถ้าระบบตรวจแล้วไม่พบข้อมูลที่ถามในหลักสูตร จะใช้ข้อความมาตรฐาน

```text
ไม่พบข้อมูลนี้ในเล่มหลักสูตร
```

ในชุด Gold Questions มีกรณีทดสอบ not-found 2 ข้อ และผลประเมินของชุด submission นี้ผ่านทั้ง 2 ข้อ

---

## 6. ขอบเขตของชุด Submission นี้

ชุดนี้เป็น **frozen submission package** สำหรับการประเมินงาน ไม่ใช่โฟลเดอร์ runtime ปกติของโปรเจกต์

ขอบเขตหลักของชุดนี้คือ

- หลักสูตร IT
- แผนสหกิจและไม่สหกิจ
- structured / semantic / hybrid QA
- provenance
- deterministic verification
- Gold Questions และ evaluation

งานพัฒนารุ่นหลัง เช่น การเข้าใจคำถามภาษาไทยที่กำกวมมากขึ้น หรือการสนทนาแบบหลายข้อความต่อเนื่อง ไม่ได้ถือเป็น requirement ของชุด submission นี้

---

## 7. ถ้าต้องการลองถามระบบ

การใช้งานระบบปกติทำจาก root ของ repository ไม่ได้ใช้ `submission/` เป็น runtime input โดยตรง

สร้าง runtime database:

```powershell
python -m rag.build_index
```

ถามหนึ่งคำถาม:

```powershell
python ask.py "IT ปี 2 เทอม 1 เรียนวิชาอะไรบ้าง"
```

หรือเปิดโหมดถามต่อเนื่อง:

```powershell
python ask.py
```

ตัวอย่าง output:

```text
ถาม: <คำถาม>
ตอบ: <คำตอบ>
แหล่งข้อมูล: <หน้าหรือไฟล์ต้นทาง>
```

รายละเอียด pipeline และวิธีติดตั้งทั้งหมดดูได้จาก `README.md` ที่ root ของ repository

## 8. สรุปสั้นที่สุด

หากต้องการตรวจเฉพาะส่วนสำคัญ แนะนำดูตามลำดับนี้

1. `curriculum.json` — ข้อมูลหลักสูตรที่ระบบใช้
2. `verify.json` — ผลตรวจคุณภาพข้อมูล
3. `gold_questions.json` — ชุดคำถามสำหรับวัดระบบ
4. `eval_result.json` — ผลการตอบคำถามจริง
5. `curriculum.db` — ฐานข้อมูลที่สร้างจากข้อมูลหลักสูตร
6. `curriculum.conversion.json` — ที่มาของการแปลง/ซ่อมข้อมูล
7. `schema/` — รูปแบบ JSON และ SQLite ที่ใช้ในระบบ

เป้าหมายของ submission นี้คือแสดงให้เห็นกระบวนการตั้งแต่ **ข้อมูลหลักสูตรที่ตรวจสอบย้อนกลับได้ → ฐานข้อมูล → การค้นหา → คำตอบที่มีหลักฐานรองรับ**
